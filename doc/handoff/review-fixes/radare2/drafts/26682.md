## Reply to trufae's 2026-09-18 comment (post on #26682)

- Took the first non-blocking point. `_add_ref` returns true on a new edge or a changed type, and `_delete_ref` returns true on a removed edge. `gen` moves only if one of the two directions changed, so a same-type re-add or a delete of a missing edge keeps the cached counts.
- That exposed a master bug in `_delete_ref`, fixed in 8af3aa2 and split out as #NEW-DEL. It erased the whole adjacency entry whenever the entry held one edge, without checking that edge was `to`. So `r_anal_xref_del (A, C)`, with only A->B stored, dropped A->B from the forward map only. The erase also leaked the `Edges` table: valgrind shows 80,000 bytes lost in 2,000 blocks for 1000 set+del pairs.
- The reset test was fixed. With two `axd` after `ax-*` it passed even with the carry deleted. It now uses one `axd`, and both it and a new unit test fail without the carry.
- ABI: appending `refsgen` still moves the fields after `meta`, because `meta` is embedded by value. `imports` goes 216 -> 224 and `sizeof (RAnalFunction)` 240 -> 256. Avoiding that needs a per-function map on the RefManager, which costs a lookup per count. OK for master now, or should this wait for the next ABI bump?

## New PR

**Title:** Invalidate cached function ref counts with an xref generation counter ##analysis

Supersedes #26682.

`afll`'s `numcallrefs`/`numrefs` are cached in `RAnalFunction::meta`. They were invalidated through `r_anal_get_function_at` on each xref endpoint, which matches only a function entry. An xref's source is almost always inside a function, so most writes invalidated nothing and the columns stayed stale.

- The ref manager keeps a `gen`, and `RAnalFcnMeta.refsgen` records the generation the counts were computed at. `r_anal_function_count_refs`/`count_xrefs` recompute when the two differ. There is no lookup on the write path, so shared blocks, block-less functions and a callee found by a later `af` are covered by construction.
- `gen` moves only when the edge set changes: a new edge or type in `_add_ref`, a removed edge in `_delete_ref`. A repeated `axC`, or an `ax-` of a missing edge, keeps the caches.
- `r_anal_xrefs_init` carries `gen` into the new manager, so counts cached before a reset cannot match again.
- `_delete_ref` no longer erases a source's only edge when it is not the one being deleted, and it frees the emptied `Edges` table (#NEW-DEL).
- `r_anal_xrefs_setf` keeps its `fcn` argument for API compatibility. It is unused.

ABI: `refsgen` is appended to `RAnalFcnMeta`, and `meta` is embedded in `RAnalFunction`, so the later fields move (x86-64: 240 -> 256 bytes).

Cost (callgrind, `aa; aan; afll; aflj; afl,` on bins/elf/bash): 1,131 recounts against 1,125 on master, +0.04% total Ir. The `afll` output is identical.

Tests:
- `db/anal/xrefs`: an xref added and removed inside a function, a block-less function, a callee seen by a later `af`, and the reset carry with one `axd`.
- `test/unit/test_anal_xrefs.c`: a delete of a missing edge, `gen` following the edge set, and the reset carry.

Results: r2r shows master + 4 OK, the unit suite 776 OK (master 773 + 3), and valgrind and ASan+UBSan are clean.

## Split-out PR

**Title:** Keep the other xrefs of an address when deleting one it does not have ##analysis

`_delete_ref` erased the whole adjacency entry when that entry held one edge, without checking it was the edge being deleted. So `r_anal_xref_del (anal, A, C)`, with only A->B stored, dropped A->B from the forward map, and the backward map no longer agreed. The erase also leaked the entry's `Edges` table: the map's value policy does not destroy values, which is why `adjacency_list_fini` frees them by hand.

It now erases `to` first, and frees and erases the table only once it is empty.

- `test_r_anal_xref_del_missing_edge` (`test/unit/test_anal_xrefs.c`) fails on master and passes here.
- valgrind on 1000 set+del pairs: master definitely loses 80,000 bytes in 2,000 blocks (+96,000 indirectly). This branch loses none.
- r2r on `db/anal/xrefs`, `cmd_ax`, `cmd_af` and `json1`: 52 OK, 2 BR, 0 XX.

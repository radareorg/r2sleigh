# #26765 Read registers and target details from lldb's debugserver ##debug (short)

## Reply to trufae's review of 2026-09-21 (pullrequestreview-5262234182)

One reply on #26765, quoting each point:

> refactor the register-reading path instead of implementing another one for LLDB

Done. `gdbr_read_registers` is the only read path: it sends `g` while the stub answers it, and otherwise one `p` for each register not yet known. `gdbr_read_registers_lldb` is gone. LLDB differs only in two capability bits, `caps.g` and `caps.thread_suffix`, and `send_reg_msg` adds the suffix for `g`, `p`, `G` and `P` alike. QThreadSuffixSupported is sent only when qSupported names an lldb extension (qEcho, QThreadSuffixSupported or QListThreadsInStopReply), so gdbserver, qemu and OpenOCD connect as before.

> Same issue with stop-reply register parsing

Done. `handle_lldb_read_reg` is gone. `handle_stop_reason` stores every `n:r` pair of a T reply through `gdbr_regs_store`, which shares its decoding with the `p` loop, and gdbserver's expedited registers take the same path. `n` is the stub's register number. It is looked up in the profile rather than used as an index, because target.xml may skip numbers, and `p` and `P` use the stub's number too. A value is kept only if every digit is hex. The stored values are dropped once `g` is in use, and when the reply names another thread.

> `gdbr_read_process_info()` is called twice on the successful attach path

It is gone, along with qProcessInfo (next point). After a successful vAttach, target.xml is read once, because the attached process decides the register layout.

> The connect path now sends `qProcessInfo` unconditionally

qProcessInfo is no longer sent. arch and bits come from target.xml: lldb-server states `<architecture>x86_64</architecture>`, and `_resolve_arch` already decodes debugserver's `com.apple.debugserver.<arch>`. The pid comes from vAttach. A stub without qXfer:features falls back to r2's arch, as on master. Against gdbserver 15.1, connect sends the same packets as master, and a unit test checks that sequence.

> `gdbr_connect_lldb()` hardcodes `g = false` without probing it anymore

`g` is now probed on the first register read, for every stub, instead of at connect. lldb-server refuses `g` until a process exists, which is why master's connect failed. `caps.g` is cleared only when `g` is refused and `p` then answers. lldb-server answers `g;thread:<tid>;`, so a read is one packet. That depends on the target.xml offsets in the first commit: lldb-server lays out `g` like user_regs_struct, and master's contiguous layout read rsp as 0.

> Avoid heap-copying every LLDB stop packet

Done, and no strdup is left. Registers are stored while `handle_stop_reason` tokenizes the packet, so `gdbr_stop_reason`, `gdbr_attach` and `send_vcont` get this just by calling it.

> The new buffer-capacity helper needs overflow handling

`gdbr_grow_size` grows to the next power of two above len+1. It refuses len >= 2^(bits of ssize_t - 2), so neither the doubling nor the store into `data_max` can wrap. The packet reader's `append()` uses it too, replacing `int newsize = g->data_max * 2`. The register block is at most 1 MiB, and each register's bit offset and size are checked against it. A register outside the block is refused, and so is a value wider than its register. A refused read returns failure, so nothing is built from the refusal. The other lengths the stub controls stay bounded too. A stop-reply register number saturates and then matches no register, and target.xml offsets are parsed as at most UT32_MAX bits. `read_packet` counts each 4 KiB chunk as a retry, so with the default 40 retries a `g` reply is at most about 160 KiB.

> The architecture parsing is narrow and duplicates architecture knowledge

The Darwin CPU-type table went away with qProcessInfo. The target-description path gained only two names: `x86_64`, and `arm64`, which the `arm` prefix match used to read as 32-bit.

> Please add protocol-level regression tests

test/unit/test_gdb.c replays stub transcripts over a socketpair, or over TCP for connect. There are 13 new cases:
- gdbserver sends one `g`, even after a T reply with registers.
- lldb `g` with the suffix, and `g` refused so that `p` goes only to the registers the stop reply lacks.
- The suffix off, and a stop reply for another thread.
- A register at bit 96 lands at byte 12.
- An oversized value, the growth limits, and a register past the block (including a wrapping offset).
- The `P`/`G` fallback without registers, and `P`, `G` and `select` naming the thread.
- A vAttach T reply without extended mode.
- target.xml offsets.
- target.xml that skips register numbers: the stop reply, `p` and `P` use the stub's numbers, and a value with unavailable (`x`) bytes leaves the register as it was.
- The connect packets of gdbserver versus lldb.

Each of 23 reverted rules fails at least one case.

## New PR

**Title:** Read registers from lldb stubs through the generic gdb client ##debug

Supersedes #26765 (the gdb-protocol half of #25935), with the review applied.

LLDB's stubs are now a capability profile of the one gdb client. Each capability is learnt from the stub's replies:
- `caps.g`: `g` is tried on the first register read, not at connect, because lldb-server refuses it until a process exists. A stub that refuses `g` but answers `p` is read one register at a time.
- `caps.thread_suffix`: QThreadSuffixSupported goes only to stubs whose qSupported names an lldb extension. Once it is accepted, `g`, `p`, `G` and `P` carry `;thread:<tid>;`.
- `handle_stop_reason` stores a T reply's `n:r` registers, so `p` skips them. The register cache moved from a file static into `libgdbr_t` and records which bytes it holds.
- `p`, `P` and a T reply's `n:r` name a register by the stub's number. target.xml states that number and may skip some (gdb's arm-core.xml puts cpsr at 25). A register profile states none, so its order is used, as `P` did on master.
- A refused read fails. It is not asked again until the thread runs or a register is written. `gdb_reg_read` no longer copies the refusal into the register arena, and the `G` write fallback needs a successful read.
- target.xml `offset` attributes are honored, because lldb stubs lay out `g` their own way. That first commit alone fixes lldb-server launch on master, where rsp read 0, rflags and cs were swapped, and `ds` failed. `x86_64` and `arm64` are recognized. qProcessInfo and the CPU-type table are gone.
- vAttach is sent without extended mode. Its T reply is parsed as a stop reply, and target.xml is read again for the attached process. Master could not connect to a program-less lldb-server with `gdb://host:port/PID`.
- `g->data` grows through one checked helper, the packet reader included, and the register block is bounded at 1 MiB.

Changes for GDB stubs (gdbserver 15.1 on x86-64, against master):
- Launch sends the same packets, minus one redundant `g`.
- With `--multi` and vAttach, target.xml is read again, so `drp` shows gdbserver's own 178 registers instead of the built-in 58. `ds` then sends `vCont;s:p<pid>.<tid>` directly.
- A stub whose target.xml skips numbers now gets `P` with the stub's number. With gdb's arm-core.xml, master's `dr cpsr=…` sent `P10=…`, which is register 16, an FPA register. gdbserver numbers its x86-64 registers without gaps, so its packets do not change. No arm stub was tested.

Tests: this was run on Linux x86-64 against lldb-server 18.1.3 and gdbserver 15.1. test/unit/test_gdb.c adds 13 transcript cases (unit suite 774 -> 787 OK), and each of 23 reverted rules fails at least one of them. ASan+UBSan report no errors, only the existing leak in `gdbr_parse_processes_xml`. 400000 mutated stop replies fed to `handle_stop_reason` under ASan+UBSan found no memory error. The only report was the existing shift in `unpack` (packet.c:43) on a non-hex checksum digit. r2r on db/cmd, io, json, tools and archos/linux-x86_64 (3760 tests) gives the same result as master for every test, but no r2r test drives a stub.

### Not tested: debugserver (needs a Mac)

debugserver was not run: there was no Apple hardware. What to check:
1. arm64: run `debugserver 127.0.0.1:PORT /bin/ls`, then `r2 -e log.level=6 -d gdb://127.0.0.1:PORT`. Check `asm.arch`/`asm.bits`, that `drp` has offsets from target.xml, `dr` against lldb's `register read`, `ds`, and `dr x0=1;dr x0`. In the log, check that qSupported names qEcho, QThreadSuffixSupported or QListThreadsInStopReply (otherwise debugserver is treated as a GDB stub and the suffix is never probed), that `QThreadSuffixSupported` gets OK, and that `g;thread:` is answered.
2. Do the same with a Rosetta x86_64 process, launched and via `gdb://…/PID`. The arch must come out x86/64 from `com.apple.debugserver.x86_64`. Check rip, rflags and rsi/rdi against lldb.
3. Check that debugserver's target.xml has `offset=`. Without it, `g` is laid out contiguously, and pseudo registers (w0…, eax…) would shift everything after them. If its `regnum=` values skip numbers, check `dr cpsr` after `ds`, and `dr x0=1;dr x0`.
4. With an older debugserver without qXfer:features, check what arch r2 picks. It falls back to r2's arch, which is wrong for a Rosetta process.
5. #26765 sent QListThreadsInStopReply, QEnableErrorStrings, QSetDetachOnError:1 and qVAttachOrWaitSupported. They are dropped here, because nothing reads their answers. QSetDetachOnError:1 did make debugserver detach instead of kill on disconnect, so if #25935 needs it, it belongs there.

## Known, not changed here

- `gdbr_set_architecture` (libgdbr.c:65) has an inverted check and never sets `target.valid`. Fixing it would freeze the built-in profile for stubs without target.xml, where the profile now follows `asm.bits`, so it wants its own PR.
- Without target.xml the profile states no stub numbers, so profile order is assumed, as `P` did on master. That is wrong for the built-in x86_64 (`fake` first) and arm32 (r13-r15 listed twice) profiles, and only a stub without target.xml that refuses `g` or answers `P` is affected.
- `G` exceeds `send_max` (2500) for x86-64 gdbserver, so the `G` write fallback fails there, as it does on master.
- `gdbr_write_reg` dereferences a NULL profile after a `W`/`X` exit (master used the freed pointer), and `handle_P` takes an `E` reply as success.
- io_gdb.c leaks the session when vAttach fails, and `gdbr_parse_processes_xml` leaks too.
